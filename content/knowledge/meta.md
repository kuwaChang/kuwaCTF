# Meta
## CTF基本フロー
1. 観測
2. 仮説立案
3. 検証
4. ログ取得
5. 再現性確認

## 仮説とは何か
### 定義
- 「こうすれば解けるのではないか？」という**予測**
### 例
- 「Base64っぽい」　-> デコードしてみる

### 仮説の立て方
1. 観測から特徴を抽出
2. 類似パターンを思い出す
3. 最も簡単な仮説を選ぶ

## 初心者が陥りやすいミス
1. 思い込み
   - Cryptoだと思い込む
2. 試行ログを残さない
   - 同じことを繰り返す

## リカバリ手順
### 進まない場合
1. 別カテゴリを疑う
2. 入力データを見直す
3. ツールを変える
4. writeupを調べる
### 具体例
- Crypto → Forensicsを疑う
- PNG → binwalk試す

## 目的
ローカルLLMがCTF学習者に対して、正確で具体的かつ教えすぎないヒントを返すための共通知識。

## これまでの評価で見えた不足

### 1. 質問意図の取り違え
- ユーザーが「最終回答だけ知りたい」と言っている場合でも、CTF学習モードでは最終フラグや完全解答を出してよいとは限らない。
- ただし、単に拒否するだけでは低評価になりやすい。
- 「最終答えは出せないが、最終段階の確認ポイント・検証方法・次に見る場所」を具体的に返す必要がある。

### 2. 問題カテゴリの混同
- `hard5` などの問題IDだけで、勝手に Web / Forensics / OSINT などを決め打ちしない。
- RAGに問題メタ情報がある場合は、そのカテゴリ・タイトル・ファイル名・ヒント文を優先する。
- RAGに根拠がない場合は「この問題IDだけではカテゴリを断定できない」と明示する。

### 3. 抽象的な一般論に逃げる
低評価になりやすい例：
- 「よく観察しましょう」
- 「ツールを使って確認しましょう」
- 「学びが大切です」

改善例：
- `file challenge.png`
- `xxd -l 16 challenge.png`
- `binwalk -e challenge.png`
- `strings -a challenge.bin | grep -i flag`
- 「PNGなら先頭8バイトは `89 50 4E 47 0D 0A 1A 0A`」

### 4. 情報開示の段階制御不足
CTFチューターでは、回答を以下の段階に分ける。

| 段階 | 内容 | 出してよい情報 |
|---|---|---|
| レベル1 | 着眼点 | 分野、見るべき場所、違和感 |
| レベル2 | 調査方法 | コマンド、ツール、確認順序 |
| レベル3 | 具体的ヒント | 重要な文字列、ヘッダ、パラメータ名など |
| レベル4 | ほぼ解法 | 変換式、復元手順、読み取り方法 |
| レベル5 | 最終確認 | フラグ形式の確認、提出前チェック |

原則として、ユーザーが「最終回答」と言っても、学習用CTFではレベル4〜5までに留める。

## 回答テンプレート

```md
### 着眼点
- ここでは `<カテゴリ>` の典型パターンを疑います。
- 特に `<具体的な違和感>` を確認します。

### まず試すこと
```sh
<コマンド1>
<コマンド2>
```

### 結果の見方
- `<出力例>` が出たら `<意味>` です。
- `<別の出力例>` の場合は `<次の確認>` に進みます。

### 次のヒント
- `<教えすぎないが進める具体ヒント>`
```

## 禁止したい回答パターン
- 根拠なしに問題カテゴリを断定する。
- フラグそのものを推測で出す。
- 「できません」だけで終える。
- ツール名だけ挙げて、何を確認するかを書かない。
- 実在しないCTFサイトやツールを例として出す。
